# TSUBAME deployment — high-res Dy164 + Eu151 scan

## TL;DR

```bash
# On the TSUBAME login node:
git clone <your-fork> /gs/bs/$USER/SpinorBEC.jl
cd /gs/bs/$USER/SpinorBEC.jl
module load cuda/12.6.0 julia/1.12.6

julia --project=. -e 'using Pkg; Pkg.instantiate()'         # one-shot

# Pre-flight (interactive node, 30 min):
qrsh -l gpu_h=1,h_rt=00:30:00
bash scripts/tsubame/preflight.sh                           # CUDA + Julia + smoke
julia --project=. scripts/tsubame/build_sysimage.jl         # optional, saves JIT cost
exit

# Generate configs + submit:
julia --project=. scripts/tsubame/generate_hires_scan.jl    # populates runs/tsubame_scan/
qsub scripts/tsubame/run_scan_array.sbatch                  # submits N-task job array
```

## Optimisations baked in

- **Sysimage support**: If `spinor_sysimage.so` is present at the project
  root, the SBATCH script picks it up and each task skips the ~30-60 sec
  SpinorBEC JIT cost. Build once via
  `julia --project=. scripts/tsubame/build_sysimage.jl` (~10-15 min).
- **JLD2 zstd compression** (default ON): snapshot bulk reduced 30-50%
  on disk + faster `rsync` back to local. Disable with
  `compress=false` kwarg if benchmarking raw I/O.
- **Node-local NVMe scratch**: `SPINORBEC_SCRATCH_DIR=$T3TMPDIR/<JOB>_<TASK>`
  routes JLD2 `.tmp` atomic-write staging away from shared FS hotspots.
- **Multi-phase canonical save**: `save_rotating_basis_result!` (called
  automatically by `run_pipeline`) writes the full GS → tilt → chirp →
  stir trajectory; no separate repack step.

## Resource estimate

- 11 jobs × ~5h average = 55 GPU-hours
- f_node=1 with 4-way concurrency → ~14h wall clock
- With H100 vs the local desktop GPU: expect 1.5-2× speedup
- Disk: psi_snapshots at 48³ × D=13 × ComplexF64 × ~60 frames ≈ 200 MB / run

## Adjustments for the actual TSUBAME profile

The `.sbatch` files use guesses for module names and CUDA paths. Verify:

```bash
module avail cuda    # find the correct CUDA module name
module avail julia   # if no julia module, install via juliaup
```

Edit `scripts/tsubame/run_scan_array.sbatch` accordingly:
- `module load cuda/X.Y.Z` → match what TSUBAME has
- `LD_LIBRARY_PATH=$CUDA_HOME/lib64` → adjust if CUDA is in a non-standard
  location (check `which nvcc` or `module show cuda/...`)
- `T3TMPDIR` → on TSUBAME 3 the local scratch env var was `T3TMPDIR`, on
  TSUBAME 4 it may differ; check the user guide.

## Pulling results back

```bash
rsync -av --include='*.jld2' --include='*/' --exclude='*' \
    user@login.t3.gsic.titech.ac.jp:/gs/bs/$USER/SpinorBEC.jl/runs/tsubame_scan/ \
    runs/tsubame_scan/

julia --project=. scripts/audit_thesis_batch.jl    # adjusted to scan tsubame_scan/
```

## What to do BEFORE submitting

1. **Wait for `dy164_main_eps1e6` to finish locally** (in flight at
   audit-write time). If ε=1e-6 result still shows m=+F: 1.0→1.0 frozen,
   the Dy164 Klaus reproduction is *real*, just deeply adiabatic. Fine to
   submit. If ε=1e-6 result is *different*, then the original Klaus run
   was a numerical artifact — investigate before committing TSUBAME GPU
   hours.
2. **Verify Project.toml + Manifest.toml match TSUBAME's Julia version**.
   If the cluster is on Julia 1.10 or 1.11 (not 1.12), instantiate may
   refuse — add a compatible version or stay on 1.12 via juliaup.
3. **CUDA driver compat**: verify `nvidia-smi` on the cluster reports a
   driver compatible with the CUDA toolkit version you `module load`.
