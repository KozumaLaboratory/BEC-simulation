## 1. `energy_gradient!` chose its backend from the wrong array

Landed in #316. `src/solvers/lbfgs/energy_gradient.jl` branched CPU-vs-GPU on
`psi`, while computing on `ws.state.psi` and writing `grad`. A ground state read
back from jld2 is a host `Array` whatever backend wrote it (`_save_gs_artifact`
stores `_to_host`), so the GS stage-cache audit — host ψ, GPU workspace — took the
CPU branch, where the registry's device buffers met a host `grad` and every
accumulate scalar-indexed.

```
nested task error: Scalar indexing is disallowed.
  [1] _grad_kinetic!   src/hamiltonian/terms/kinetic.jl:86
  [5] verify_verdict   src/model/verdict_truth.jl:116
```

So the audit could never run on GPU at all.

**Why nothing caught it, and the general shape.** It needs a cache **hit**. The run
that populates the stage cache computes its ground state and never reaches the load
path, so *only the second GPU run of a given ground state dies* — and only if its
`ground_state` block is byte-identical to an earlier one. A defect on a
cache-hit-only path is invisible to any test that builds its own fixture.

Gated by `test/gpu/test_gpu_energy_gradient_host_psi.jl` (full tier), which asserts
GPU == CPU **value** rather than "does not throw", covers the production
`verify_verdict` shape, and checks it still **rejects** a wrong energy. Canaried by
reverting the branch key.

Coverage caveat, stated because the green checks do not say it: no CI job runs on a
GPU, so that file — like every `gpu/` file — is a no-op in per-PR CI and in nightly.
It was verified on the local WSL2 card.

## 2. An agent has no clock

`scripts/watch_until_done.sh`, landed in #319.

"I'll report when it's done" is empty unless a process is left running whose
**exit** supplies the turn. Polling inside one turn dies with the turn. This was
demonstrated the same day: a completion report was promised for a CI run with
nothing watching it, while the memory entry covering exactly that was already
indexed.

Second half of the same problem: **a partial classifier states a verdict at the
moment it has no information.** Five prior incidents in this project did that. So
the tool has four verdicts — GREEN / RED / TIMEOUT / UNKNOWN — absence is its own
verdict, a deadline is not green, and `--canary` proves RED and UNKNOWN are
reachable before a GREEN from it is worth anything.

Three bugs surfaced by running it against real data rather than reasoning about it:

- `qacct` prints `failed` **before** `exit_status`. Emitting on `failed` read the
  *previous* array task's exit code, and for the first task read it unset — which
  awk compares equal to 0. **A nonzero exit would have been reported as success.**
- Backticks in a comment inside a double-quoted `ssh "..."` string are executed.
- The TIMEOUT canary raced a live CI run: a queued run's jobs have not materialised,
  so the query is empty — UNKNOWN, not TIMEOUT. It now uses a local sleeping pid,
  pending by construction.

`local-pid` requires `--rc-file` because **a PID disappearing says nothing about
success** — that is the shape of an OOM kill, and it reports UNKNOWN.

## 3. The memory index had been silently truncated

`MEMORY.md` was **43 % over its 24.4 KB load limit** (35618 bytes), so **55 of its
133 lines — 41 % of the index — had not been loaded in any session.**

Silent in the worst way: the warning names the file, not the entries that fell off
the end. There is no way to notice from inside a session that a rule one is supposed
to follow was never in context.

**Consequence for where rules live.** A rule that must fire every session belongs in
`CLAUDE.md`, which is loaded in full. Memory is the per-incident layer and is
*discoverable*, not executed — and may not even be loaded. `CLAUDE.md` now carries
the limit, the verbatim-move procedure, and the check.

Fixed to 23982 bytes by moving 33 dated gotchas and 4 older mistake entries
**verbatim** into `memory_index_gotchas_dated.md` and the existing
`memory_index_mistakes_recent.md`. Verified both directions: 0 of 107 index items
absent from the union of index + sub-indexes, 0 links lost (152 → 153), reachability
unchanged at 264/280 live and 62/75 archived.

## 4. The six corrections, and their classes

| # | What happened | Cost | Class |
|---|---|---|---|
| 1 | Fitted the experiment without reading the paper — all six premises were in Results and Appendices D/E | 24 arms, ~3 h GPU | acted on a model of the situation instead of verifying it |
| 2 | Row-normalised the published data, dividing out the atom-number decay under test; reported the best-agreeing component as the worst | rms 0.263 vs 0.094 | **a normalisation removed the quantity being measured** |
| 3 | Read a residual at one point on an axis carrying a ±10 nT systematic | 6 arms | the systematic binds the axis held **fixed**, not only the one scanned |
| 4 | Counted 21 retracted configs as 24 — a word search matched three live files that *cite* the retracted ones; the README had said 21 all along | — | **the regex became the measurement** |
| 5 | Patched `Bz` at the inline site when the scan override decides it | caught pre-launch | one of two sites |
| 6 | Read `git diff origin/main..HEAD` as this branch's diff: 187 files, thousands of deletions — 17 commits of main's own progress seen across two divergent trees | — | **the regex became the measurement** |

Two things worth extracting.

**#4 and #6 are one class, and it fired three times in one day** (the third being a
`grep -E "^[+-][^+-]"` that excluded its own target lines because they began `+-`).
A search whose result is used as a count must be checked against an independent
count — here the README's own number, and `git merge-base`. When a correction always
moves in one direction, the rule has become the measurement.

**#2 and #3 are the two ways an instrument silently changes the answer**: one by
projecting out a degree of freedom (normalisation), one by reading a difference
smaller than the uncertainty on a coordinate being held still. Both produced
self-consistent, confident, wrong numbers from healthy machinery.

**What the gates bought.** 2026-08-02: 24 arms, ~3 h GPU, every premise wrong.
2026-08-04: 6 arms, 36 min GPU, each with its rejection criterion written into the
config before launch, and the negative result (`c1_ratio` is excluded) is the useful
one. Same question, same code.
